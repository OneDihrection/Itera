# Tuntun architecture

How the Tuntun iPad app is put together: where code lives, how dependencies reach each screen, how navigation works, and how a guided session runs. This is a guide for developers.

## 1. Overview

Tuntun is a guided rehabilitation exercise app for one patient per installation, set up by a caregiver.

| Aspect | Choice |
| --- | --- |
| Platform | iPad, iPadOS 17 or later, landscape only |
| Data | Local only: no accounts, backend or cloud sync |
| Runtime resources | Bundled: exercises, ML models, narration and animations work offline |
| Project | One app target generated by XcodeGen from `project.yml`; the `.xcodeproj` is not committed |
| UI pattern | SwiftUI + MVVM with Observation, feature builders and feature routers |
| Languages | Indonesian (default) and English through String Catalogs |

The architecture follows the iOS Conference Indonesia 2026 MVVM sample (builders, dependency protocols, routers), adapted to Observation, sheets and a full-screen plan cover.

## 2. Source layout

```text
Tuntun/
  MyApp.swift
  App/            AppComponent (composition root), RootBuilder, RootView + TabRouter
  DesignSystem/   reusable controls and styling (read its README first)
  Shared/         app-wide infrastructure: Tracking, Audio, Animation, Storage,
                  Permissions, Localization, Accessibility
  Features/
    Routine/      exercise catalog and saved programs/settings
    Home/         Beranda, today's plan, its intro/rest pages and settings
    History/      the Progress tab: history, reports, replays, recovery
    Therapy/
      Session/    the guided session engine, storage and screen
      Shared/     ActivityLifecycle, Movement primitives, ScriptedRepetitions
      Activities/<Name>/   one flat folder per activity
  Resources/      asset catalogs, Animations, Audio, Localization, ML models
```

Inside a feature, files are grouped by kind. A kind folder exists only when it has files; activity folders stay flat.

| Folder | Holds | Rule |
| --- | --- | --- |
| `Models/` | Values, configurations, events, snapshots, engines, counting rules | Foundation only: no SwiftUI, UIKit, Combine, AVFoundation, Vision or file access |
| `Storage/` | Repository protocol, its `Local…` implementation, versioned Codable records | Uses `Shared/Storage` for atomic files |
| `Services/` | Feature-owned `…Service` types | No UI |
| `ViewModels/` | `@Observable` screen models and their `…ViewModelProtocol` | Coordinate services; no duplicated exercise rules |
| `Views/` | Layout, bindings, accessibility, forwarding actions | No counting, timers, inference, file or audio work |
| `Navigation/` | The feature's `…Builder`, its `…Dependency` protocol, its router and routes | See sections 4 and 6 |

## 3. Dependency direction

```text
                        +-------------+
                        |     App     |   constructs everything, conforms to
                        +-------------+   every feature's …Dependency
                               |
                               v
                        +-------------+
                        |    Home     |   nothing depends on Home
                        +-------------+
                        /      |      \
                       v       v       v
              +---------+ +---------+ +------------------------+
              | Therapy | | Routine | | History (recovery only)|
              +---------+ +---------+ +------------------------+
                   |           ^               |
                   +-----------+               v
                   Therapy -> Routine     History -> Therapy, Routine

        DesignSystem and Shared depend on no feature.
```

- Sessions report back to today's plan only through `DailyPlanSessionReporting`; Therapy never names a Home type.
- Routine reads Therapy's finger-session storage only.
- These are conventions inside one target, not compiler-enforced modules.

## 4. Composition root and builders

```text
MyApp
  └─ AppComponent                      Tuntun/App/AppComponent.swift
       │ builds services, repositories and shared models once
       │ conforms to HomeDependency, HistoryDependency, TherapySessionDependency
       │
       ├─ lazy homeBuilder    = HomeBuilder(dependency: self)
       ├─ lazy historyBuilder = HistoryBuilder(dependency: self)
       ├─ lazy sessionBuilder = TherapySessionBuilder(dependency: self)
       └─ lazy rootViewModel
            │
            v
       RootBuilder.buildRoot()  ──>  RootView (TabView)
                                       ├─ homeBuilder.buildHome()       ─> TMHomeView
                                       └─ historyBuilder.buildReports() ─> TMFingerReportsView
```

**`AppComponent`** is the composition root. It constructs every concrete service and repository once and exposes them through feature dependency protocols. It is never placed in the SwiftUI environment and never passed to feature code.

**`…Dependency` protocols** sit beside each builder and list only what that feature uses. For example:

```swift
@MainActor
protocol HistoryDependency {
    var fingers: FingerHomeViewModel { get }
    var sessions: any SessionRepository { get }
    var fingerReplayRepository: any FingerSessionRepository { get }
}
```

A feature that shows another feature's pages receives that feature's builder through its dependency; Home receives `sessionBuilder` to fill the plan cover.

**Builders** (`HomeBuilder`, `HistoryBuilder`, `TherapySessionBuilder`) take `any …Dependency`, store it as `private let dependency`, and create every view model and view in their feature. Views and view models never construct other view models. Stack-owning screen models (`HomeScreenViewModel`, `ReportsViewModel`, `RootViewModel`) are lazy properties, created once.

**Injection** is always through an explicit `init` that lists the dependencies, stored as `private let`. Services are named `…Service` with a `…ServiceProtocol` where there is a real substitution boundary (`permissionService: any PermissionServiceProtocol`).

**Content builders.** A screen that builds rows, destinations, sheets or cover pages is generic over a `…ContentBuildable` protocol with associated view types (`HomeContentBuildable`, `PlanCoverBuildable`, `HistoryContentBuildable`, …). The real builder conforms in the app; previews pass small mock builders.

## 5. Screens and view models

Every screen model is a `@MainActor @Observable final class` behind a `…ViewModelProtocol: AnyObject, Observable`. The view is generic over that protocol and keeps the model in `@State`:

```swift
struct TMHomeView<
    ViewModel: HomeViewModelProtocol,
    Builder: HomeContentBuildable
>: View {
    @State private var viewModel: ViewModel
    private let builder: Builder

    init(viewModel: ViewModel, builder: Builder) {
        _viewModel = State(initialValue: viewModel)
        self.builder = builder
    }
}
```

- Observation is the UI source of truth. `ObservableObject`, `@Published` and `@StateObject` are not used.
- Previews use `@Observable` mock models; the guided session uses snapshot fixtures (`SessionPresentationFixtures`, Debug only).
- Reusable controls and styling live in `Tuntun/DesignSystem` and accept values, bindings, content and actions, never feature view models or repositories. Text uses `.typography(...)`.
- `body` stays focused on composition; sections become private computed views or dedicated subviews.

## 6. Navigation

Each feature owns its navigation through an `@Observable` router in its `Navigation/` folder. **The router owns the navigation state** and changes it directly; there are no closure hooks to wire.

| Router | State it owns | Received by pages as |
| --- | --- | --- |
| `HomeRouter` | `path: [HomeRoute]`, `sheet: HomeSheet?`, `cover: PlanCover?` | `HomeRouterProtocol`, `DailyPlanRouterProtocol`, `SessionRouterProtocol` |
| `HistoryRouter` | `path: [HistoryRoute]` | `HistoryRouterProtocol` |
| `TabRouter` | `selectedTab: AppTab` | `TabRouterProtocol` (cross-tab navigation) |

### How a navigation call flows

```text
HistoryCellViewModel
  router.showSessionReport(id:)         (as any HistoryRouterProtocol)
        |
        v
HistoryRouter (@Observable)
  path.append(.sessionReport(id))
        |  observed through
        v
ReportsViewModel.path { get set }       forwards to router.path
        |
        v
TMFingerReportsView
  NavigationStack(path: $viewModel.path)
    .navigationDestination(for: HistoryRoute.self)
        |
        v
builder.buildSessionReport(id:)
```

The stack-owning screen declares `NavigationStack(path:)`, `.navigationDestination`, sheets and covers from properties on its view model. Those properties forward to the router:

```swift
var path: [HomeRoute] {
    get {
        router.path
    }
    set {
        router.path = newValue
    }
}
```

Because the state lives in the router, it survives a rebuilt view model, and any page holding the router's protocol can navigate without knowing who displays the stack.

### Rules

- Pages and view models receive the router through their initializer, typed as the narrowest `…RouterProtocol` they need.
- Destinations are built only by the feature's builder.
- Never read a router from the SwiftUI environment.
- Cross-tab navigation goes through `TabRouterProtocol`. `TabRouter.showProgress()` switches tabs silently; a tab-bar tap goes through `RootViewModel.selectedTab`, which also plays the click.

### The plan cover

Today's plan runs inside one full-screen cover, `TMPlanCoverHost`. `PlanCover` keeps its `id` while its `route: PlanCoverRoute` changes between sessions, summaries, rest and the next intro, so the cover stays mounted and only its page changes:

```text
presentCover(.therapySession(routine))
        │
        v
replaceCover(with: .planNext)      same cover id, new page
        │
        v
replaceCover(with: .fingerSession) same cover id, new page
        │
        v
endRun()                           cover = nil, sheet = nil, path = []
```

Sheets and covers re-apply button feedback, typography and the sound button style through `modalEnvironment`.

## 7. Services, storage and threading

| Component | Owns |
| --- | --- |
| `SessionEngine` | Guided progression, deadlines, suspension, set ordering, results: `handle(event) -> transition` |
| `TherapyActivity` conformers | Their own calibration, geometry, evidence acceptance and counting |
| Session view models | Service coordination, effects, presentation mapping |
| `BodyTrackingService`, `HandCameraService` | Capture, inference, subject selection, frame freshness, clip frames |
| `SessionAudioService`, `GuidanceAudioService` | Narration, counts, effects, music, voice commands |
| `PermissionService` | Camera, microphone and speech authorization |
| `FingerSessionService` | Prepares and holds the open finger or forearm session |
| `HistoryRecoveryService` | Finalizes a session interrupted by termination, once per launch |
| Repositories | Routines, sessions, finger sessions, daily-plan progress |

**Reactivity.** Observation drives the UI. Combine carries asynchronous service events; subscriptions are cancelled when the session ends. Domain transitions are ordinary typed calls with typed values (`SessionEvent`, `SessionSnapshot`, `SessionEffect`, `TrackingObservation`, …).

**Threading.** View models and engine mutations run on the main actor and stay short. Per-frame inference and file I/O run off the main thread. One capture owner delivers only the latest result; superseded frames are dropped, never queued.

**Storage.** Atomic, versioned JSON files through `Shared/Storage` (`AtomicJSONFiles`). A missing file differs from an unreadable one, which is never overwritten with defaults. Calibration is never persisted.

## 8. Session flow

```text
intro ─> readiness ─> calibration ─> countdown ─> practice
                                                     │
            ┌────────────────────────────────────────┘
            v
      set done / rest ─> next set or side ─> summary
                                                │  (daily plan)
                                                v
                                     long rest ─> next intro ─> …
```

- **Readiness** validates permissions and on-device voice recognition before any capture.
- **One camera preview** stays mounted through every stage of an activity.
- **Pause and Stop** are available by touch at every stage; the voice command "stop" pauses and "go" resumes.
- **Completion** of an activity is recorded once as completed, skipped or interrupted. A session that reached its goal marks its plan item done through `DailyPlanSessionReporting`.

Where it lives: progression in `Features/Therapy/Session/Models/SessionEngine.swift`; exercise rules in `Features/Therapy/Activities/<Name>/`; coordination in the session view models.

## 9. Recipes

### Add a page to a feature's stack

Example: a new page on the Progress stack.

1. Add a case to the route enum: `HistoryRoute.myPage(UUID)` in `HistoryRouter.swift`.
2. Add a method to the protocol and router: `func showMyPage(id: UUID)` which does `path.append(.myPage(id))`.
3. Add `buildMyPage(id:)` to `HistoryContentBuildable` and implement it in `HistoryBuilder`, creating the page's view model there.
4. Handle the case in the screen's `.navigationDestination(for: HistoryRoute.self)` switch, calling the builder.
5. Call `router.showMyPage(id:)` from whichever view model needs it; it already holds `any HistoryRouterProtocol`.
6. Update the preview mock builder so previews still compile.

### Add a sheet or cover to Beranda

Add a case to `HomeSheet` or `PlanCoverRoute`, a method on `HomeRouter` (and the narrow protocol that callers use) that sets `sheet` or calls `replaceCover(with:)`, and the matching builder method and switch case in `TMHomeView` or `TMPlanCoverHost`.

### Add a service

1. Create `MyService` (and `MyServiceProtocol` only if it is substituted in previews or elsewhere) in `Shared/` or the feature's `Services/`.
2. Construct it once in `AppComponent`.
3. Add `var myService: …` to each `…Dependency` protocol that needs it; `AppComponent` already conforms.
4. Pass it from the builder into the view model's `init`, stored as `private let myService`.

## 10. Verification

There is no automated test target. Verify a change with:

```sh
xcodegen generate
xcodebuild -project Tuntun.xcodeproj -scheme Tuntun \
  -destination 'generic/platform=iOS Simulator' \
  IPHONEOS_DEPLOYMENT_TARGET=17.0 build
```

A Simulator build never establishes camera, voice, animation, timing or offline acceptance. Those require the physical M1 iPad, recorded with device, OS, app version, scenario and result in the design log.
