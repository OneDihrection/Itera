# Tuntun — System Design

Status: current-state specification, rewritten 2026-11-16. Every agent reads this whole document before planning, reviewing or changing the project.

This document states what is true now. [Documentation/DesignLog.md](Documentation/DesignLog.md) keeps the reasoning, the superseded rules and each change's verification evidence, oldest first; "(log: *Title*)" points at an entry there. When this document and the log differ, this document wins. A change that alters a rule here updates the rule here **and** appends a dated log entry. Explicit user instructions take precedence over both; surface conflicts rather than departing silently.

## 1. Product and constraints

- Guided exercise app for one patient per installation, set up by a caregiver who positions the device and helps with recovery. No accounts, patient selection, backend or cloud sync (ADR-001).
- iPad, iPadOS 17 or later, landscape left and right only. Mac Catalyst is retained as an exception; the M1 iPad is the minimum physical performance-validation device.
- Exercises: the finger program (five finger movements and forearm rotation), arm raise, elbow bend, directional reach, cross midline, external and internal rotation, shoulder flexion, sit to stand and fold towel.
- Camera evidence is an exercise aid, not a validated clinical measurement. Angles are 2D estimates shown with "≈" and called "observed range", never ROM.
- Sessions work offline. Every exercise, detection, narration and animation resource is bundled. Nothing is synthesized or sent over the network at runtime.
- Camera, microphone, speech-recognition authorization and en-US on-device command recognition are mandatory before therapy. There is no touch-only bypass.
- Indonesian (default) and English, through String Catalogs. The selected language is frozen during a session.

## 2. Glossary

- **Caregiver:** configures, positions the iPad and assists. Not interchangeable with patient.
- **Routine:** a saved, reusable configuration of activities and goals. Not live progress.
- **Daily plan:** today's ordered list of exercises on Beranda (`DailyPlan.standard`), run one after another.
- **Session:** one attempt at a routine snapshot. Later edits never change its history.
- **Activity:** one configured exercise on one anatomical side, or on both sides taking turns. A bilateral configuration is one activity whose sides alternate after every repetition (log: *Bilateral exercises alternate sides*).
- **Set:** a block of repetitions within an activity, followed by rest.
- **Calibration:** capturing the start position and demonstrated endpoints for the current activity and camera setup. Not a clinical assessment.
- **Observed target:** a position derived from stable calibration evidence. Never "maximum range of motion".
- **Repetition:** one accepted start → target → start cycle. **Round:** one reach sequence (right, left, up, each with its return).
- **Practice time:** time credited from usable evidence, excluding pauses, camera waits and lost tracking.
- **Session summary:** a persistent record of goals, completed work and outcomes.
- **Key repetitions:** the first, hardest and last repetition of a set, kept as skeletons and optional clips for clinicians.

## 3. Architecture

### Target and features

One app target generated by XcodeGen from `project.yml` (ADR-007). No packages, test targets or extra targets. The project spec is the source of truth; the generated `.xcodeproj` is ignored.

```text
Tuntun/
  MyApp.swift
  App/            AppComponent (composition root), RootBuilder, RootView + TabRouter, DebugScreenLauncher
  DesignSystem/   reusable controls and styling (read its README first)
  Shared/         app-wide infrastructure: Tracking, Audio, Animation, Storage, Permissions, Localization, Accessibility, Logging
  Features/
    Routine/      exercise catalog (TherapyKind, FingerExercise, BalanceExercise) and saved programs/settings
    Home/         Beranda, today's plan, its intro/rest pages and settings
    History/      the Progress tab: history, reports, replays, interrupted-session recovery
    Therapy/
      Session/    the guided session engine, session storage and the guided session screen
      Shared/     ActivityLifecycle, Movement primitives, ScriptedRepetitions
      Activities/<Name>/   one flat folder per activity (logic, its views, and its session if it has its own)
  Resources/      asset catalogs, Animations, Audio, Localization, ML models
```

### Folder rules

Inside a feature, files are grouped by kind. Create a kind folder only when it has files; activity folders stay flat.

| Folder | Holds | Rule |
| --- | --- | --- |
| `Models/` | Values, configurations, events, snapshots, engines, calibration and counting rules | Foundation only: no SwiftUI, UIKit, Combine, AVFoundation, Vision or file access |
| `Storage/` | A repository protocol, its `Local…` implementation and its versioned Codable records, side by side | Uses `Shared/Storage` for atomic files |
| `Services/` | Feature-owned services (`…Service`, with `…ServiceProtocol` when substituted) | Same rules as Shared services; no UI |
| `ViewModels/` | `@Observable` screen models and their `…ViewModelProtocol` | Coordinates services; no duplicated exercise rules |
| `Views/` | Layout, bindings, accessibility, forwarding actions | No counting, timers, inference, file or audio work |
| `Navigation/` | The feature's `…Builder` with its `…Dependency` protocol, and its router with routes | See section 4 |

The Foundation-only rule also applies to logic files in flat activity folders; they may still log through `LogManager`. Keep distinct responsibilities in dedicated files without mechanically splitting tiny related types.

### Dependency direction

- App constructs every concrete service, repository and shared model, and conforms to each feature's `…Dependency`.
- Home → Routine, Therapy (its builder and `DailyPlanSessionReporting`), History's recovery and plan-history contracts (`LocalDailyPlanProgressRepository` implements `DailyPlanHistoryRepository`, which History reads and uses to remove a deleted exercise's done mark through `removeCompleted(_:on:)`).
- Therapy → Routine. Sessions report to the plan only through `DailyPlanSessionReporting`; Therapy never names a Home type.
- History → Therapy's session and finger-session reading types, Routine.
- Routine → Therapy's finger-session storage only (`FingerHomeViewModel` reads finger history and checkpoints). DesignSystem and Shared depend on no feature.
- Nothing depends on Home.
- These are conventions within one target, not compiler-enforced modules (ADR-002).

They share `BreathingRest` and `GuidanceGate` (Therapy/Shared/SessionFlow) with the guided engine. The redesign's core (Phases 0–4, which made the guided engine a single-owner state machine) is complete; moving them fully onto the shared flow types is optional (Phases 5–9 in [Documentation/SessionFlowRedesign](Documentation/SessionFlowRedesign/README.md)), and until such a phase lands, the current behaviour described here is authoritative (log: *Stages carry their data*).

### Threading and reactivity

- View models are `@MainActor @Observable final` classes. Do not use `ObservableObject`, `@Published` or `@StateObject`. Observation is the UI source of truth (ADR-003).
- Combine carries asynchronous service events. Subscriptions are owned and cancelled when the session ends. Domain transitions are ordinary typed calls.
- Engine mutations are serialized on the main actor and stay short. Per-frame inference and file I/O stay off the main thread. One capture owner delivers the latest result with bounded work; superseded frames are dropped, never queued.
- Typed values only cross boundaries: `SessionCommand`, `SessionEvent`, `SessionSnapshot`, `SessionEffect`, `TrackingObservation`, `TrackingAvailability`, `AudioEvent`, `Routine`, `SessionSummary`. Never route strings through the camera layer.

## 4. Composition and navigation

- **Root.** `AppComponent` (App) constructs shared services once and conforms to `HomeDependency`, `HistoryDependency` and `TherapySessionDependency`. It holds each feature builder lazily (`HomeBuilder(dependency: self)`), plus app lifecycle calls. It is never placed in the environment or passed to feature code. `RootBuilder` builds the tabs from the feature builders.
- **Dependencies.** Each feature declares a `@MainActor protocol …Dependency` beside its builder, listing only what that feature uses. A feature that needs another feature's pages receives that builder through its dependency (Home receives `sessionBuilder`).
- **Naming.** Name services the way the reference project does: a service type is `…Service`, its protocol (when there is a substitution boundary) is `…ServiceProtocol`, and an injected service is stored and passed as `…Service`, for example `permissionService: any PermissionServiceProtocol`, `audioService: SessionAudioService`. Repositories keep `…Repository`; shared view models, routers and builders keep their own suffixes.
- **Builders.** `HomeBuilder`, `HistoryBuilder`, `TherapySessionBuilder` take `any …Dependency`, store it as `private let dependency`, and create every view model and view. Views and view models never construct other view models. Stack-owning screen models (`HomeScreenViewModel`, `ReportsViewModel`, `RootViewModel`) are created once, as lazy properties of their builder or of `AppComponent`.
- **Content builders.** A screen that builds rows, destinations, sheets or cover pages is generic over a `…ContentBuildable` protocol with associated view types (`HomeContentBuildable`, `PlanCoverBuildable`, `DailyPlanNextContentBuildable`, `HistoryContentBuildable`), so previews can pass mock builders. Do not add a `…Buildable` protocol that no view is generic over.
- **View-model protocols.** Each screen's model conforms to a `@MainActor …ViewModelProtocol: AnyObject, Observable`; the screen is generic over it and keeps it in `@State` (rows hold it as a plain `let`). Previews use `@Observable` mocks; the guided session uses snapshot fixtures (`SessionPresentationFixtures`, Debug only).
- **Routers.** `@Observable` objects in each feature's `Navigation/` that own the feature's navigation state (stack path, sheet, cover, selected tab) and change it directly. The screen that owns a stack declares its `NavigationStack(path:)`, destinations, sheets and covers from its view model, whose properties forward to the router; there are no closure hooks to wire (log: *Routers own navigation state*). `HomeRouter` serves Beranda's sheet, the plan intro and the plan cover; pages receive it as `HomeRouterProtocol`, `DailyPlanRouterProtocol` or `SessionRouterProtocol`. `HistoryRouter` serves the Progress stack (finger and session reports, and a day's progress page, `practiceDay`) and the floating exercise detail panel (`exerciseDetail`); the root's calendar days open a day through `ReportsViewModel`, and the day page's cards open the panel through `HistoryRouterProtocol`. The stack owner, `TMFingerReportsView`, declares the panel as an overlay over its whole stack from that router state, as it declares its destinations (log: *Exercise detail panel*). Cross-tab navigation goes through `TabRouterProtocol`. Never read a router from the environment.
- **Plan cover.** The plan runs in one full-screen cover (`TMPlanCoverHost`) that stays mounted while `PlanCover.route` changes between sessions, summaries, rest and the next intro. Sheets and covers re-apply button feedback, typography and the sound button style through `modalEnvironment`.

## Navigation, typography, and code conventions

Use KISS and YAGNI: clear names, straightforward control flow, guard clauses, focused helpers, and no speculative frameworks or extension points. Use protocols at real substitution boundaries; avoid service locators, global mutable dependencies, generic base view models, a universal event bus and one protocol per helper. The one shared instance is `LogManager.shared`: it holds only immutable values and is reached directly, not injected (log: *Shared log manager*).

Each feature owns its navigation through its router. The screen that owns a stack declares its `NavigationStack(path:)`, `.navigationDestination`, sheets and covers from state on its screen view model, and that view model exposes that state by forwarding it to the feature's `…Router`, which owns it. Every other page and view model on that stack receives the router through its initializer as a `…RouterProtocol`, and destinations are built only by the feature's builder. Never read a router from the environment; cross-tab navigation goes through `TabRouterProtocol`. Native SwiftUI layout remains allowed.

Use .typography(...) or inherit the root body style for app-authored text. Font names and direct font styling belong only in DesignSystem/Typography.

Reusable UI controls and styling belong in Tuntun/DesignSystem. Read its README first, reuse suitable components, and create a reusable component there before use when none fits. Components accept values, bindings, content and actions, never feature view models, repositories or exercise logic. Therapy-specific compositions may stay in their feature.

Keep body focused on composition. Prefer named private computed view properties, using @ViewBuilder for conditional or multiple-view sections, or dedicated subviews for meaningful sections with inputs, bindings, state, reuse, or substantial complexity. Reusable controls belong in DesignSystem; avoid splitting trivial expressions mechanically.

Inject dependencies through an explicit initializer. A type that receives services, repositories, view models, factories or factory closures declares an `init` listing them, with any plain value inputs, and stores them as `private let` (`@Bindable private var` or `@State private var` where bindings or ownership require it). Do not rely on memberwise initializers for injection. Pages are built only by their feature's builder (`…Builder`), which receives its parent's services through the feature's `…Dependency` protocol; the root, `AppComponent`, constructs shared services once and conforms to those protocols. Never place `AppComponent` or a builder's dependency in the environment or pass `AppComponent` to feature code. Subviews that take only values or a model from their parent may keep memberwise initializers. Name services the way the reference project does: a service type is `…Service`, its protocol (when there is a substitution boundary) is `…ServiceProtocol`, and an injected service is stored and passed as `…Service`, for example `permissionService: any PermissionServiceProtocol`, `audioService: SessionAudioService`. Repositories keep `…Repository`; shared view models, routers and builders keep their own suffixes.

Every newly authored file must have a format-appropriate header with its filename, actual author, and creation date. Use an explicitly supplied author first, otherwise effective git config user.name; ask if neither exists. Never hard-code a team member or use the AI's name. Preserve existing creation authorship. Swift uses Xcode-style // Created by headers; YAML uses comments and Markdown uses HTML comments. Preserve copied binaries and third-party licenses unchanged and document their source separately; never corrupt formats without comment support.

Prefer readable multiline declarations, calls, expressions, and compound conditions when they improve scanning. Put complex arguments and conditions on separate lines. Use generous blank lines between logical steps and declarations while keeping closely related statements together. Expand control-flow bodies onto separate lines; avoid compressed guards, branches, and nested ternaries.

Keep control flow shallow through guard clauses, early returns, and focused, meaningfully named helpers. Preserve clear exhaustive switches when appropriate. Do not mechanically extract trivial expressions or impose arbitrary nesting limits.

Treat readability and runtime performance as equally important. Choose clear algorithms and appropriate data structures, avoid unnecessary repeated work and allocations in frequently executed paths, and preserve the architecture's threading and bounded-work requirements. Base performance-driven complexity on measurements or concrete workload constraints. Document non-obvious tradeoffs and verify that refactors preserve behavior and performance characteristics.

Use /// Markdown API documentation when helpful and // MARK: - sections in longer files. Comment non-obvious purpose, constraints, and lifecycle behavior rather than restating syntax.

## 5. Session lifecycle

```text
intro → readiness → calibration (camera visible, cues spoken over it) → countdown
      → practice → set done / rest → next set or side → summary → (plan) long rest → next intro
```

- **Readiness.** Beranda's Mulai Latihan or a card opens the item's intro, which narrates first: the scripted brief for Indonesian arm raise and thumb opposition, otherwise the exercise's purpose (`plan.purpose.<item>`). Start stays enabled: tapping it while the intro plays skips the rest and opens the session, otherwise the session opens automatically when it ends; a later Start no longer replays it (log: *Start skips the plan intro narration*). The after-rest intro of an unscripted exercise shows its countdown instead of narrating. Start (or that automatic start, or the one after a long rest) validates permissions and listening through `TherapyReadinessViewModel` before any capture (log: *Narrated plan intros*). Session entry validates readiness again. Home never listens while idle.
- **One preview.** One camera preview stays mounted through every stage of an activity; the layout depends on activity kind, never stage. Capture stops at summary or exit.
- **Guidance gates.** Opening and demonstration cards advance only after identified narration completes or fails and measured reading completes (VoiceOver needs explicit acknowledgment), then a short pause. Arm raise, elbow bend, directional reach and fold towel run these cues over the camera with no text, so they wait for narration alone (log: *No calibration card on the camera*). The pause is `SessionGuidance.defaultQuietDelay` (1.5 s) after an opening cue, `SessionEngine.demonstrationHold` (3 s) after a demonstration (log: *Responsive narration hand-off*). Only these opening cues, "try the movement", "calibration complete" and the countdown cue gate evidence. Once calibration starts, body exercises never wait for narration, as in Balancing: captures, holds and repetitions run while a cue plays (log: *Body exercises do not wait for narration*). While a cue does hold evidence back, the guided session still passes frames to the activity as display-only previews (`ActivityEvent.preview`), as Balancing does, so the joint and bubbles stay drawn and follow the patient over the camera through the opening cues, "try the movement", "calibration complete" and the countdown cue; nothing is credited from them (log: *Indicator visible during narration*). Replayed or interrupted guidance gets a new identity; stale callbacks never advance. Arm raise, elbow bend and reach use a five-second preparation before calibration; countdowns are three seconds (five before a later set of the Indonesian arm-raise script) and start after their cue is spoken. In guided sessions `SessionEngine` runs the one countdown for every activity: it ends on the first event at or after its end, a pause or camera wait stops it, and it restarts from its full length after its cue is spoken again (ADR-010). Fold towel has no calibration or preparation: its opening and demonstration cues (`towel.opening.<side>`, `towel.demo`) are spoken over the live camera as the other light exercises' are, under the exercise heading, then its countdown (log: *Fold towel opening over the camera*). The countdown stays a full-screen cover; beneath it, and during the cue before it, the target is drawn quietly until practice starts (log: *Responsive narration hand-off*).
- **Suspension.** Pause and Stop are available by touch at every stage; "stop" by voice pauses. Resume is explicit. A normal pause keeps calibration and completed work and clears pending holds and incomplete cycles. Backgrounding pauses, stops capture and listening and cancels narration; foregrounding never resumes automatically. Audio interruptions and lost command recognition pause and block resume until listening is validated. In guided sessions `SessionEngine` owns suspension (`Suspension`: pause and camera-wait reasons, voice and storage blockers): view models report blockers and never decide or refuse Resume themselves; a newly reported blocker pauses. Skip and Stop never lift a pause or camera wait; a skipped set's feedback plays after Resume (ADR-010).
- **Camera waits.** Scoring rejects observations older than 300 ms, from an older capture generation, non-finite or non-increasing. Readiness waits `SessionEngine.cameraWaitGrace` (1 s) without a fresh frame before a camera wait, which freezes deadlines and evidence. Capture or preview loss waits at once. After the frame watchdog or a capture runtime error, capture restarts once automatically; the session still waits for explicit Resume. Missing patient evidence alone never opens Pause, in body or finger sessions (log: *Detection waits without automatic pause*).
- **Loading.** Starting and leaving a session cover the screen with `TMLoadingOverlay` ("Menyiapkan latihan…" / "Menyelesaikan latihan…"): from the intro's Start (`TherapyReadinessViewModel.preparingSession`) until each session's `start()` has prepared audio, listening and capture (`isStarting`/`isPreparing`), and from End or leaving the summary (`end()`, `leave()`, `isFinishing`) until the page is replaced or the stopped summary is saved; the finger all-done page shows it while saving. The owner raises its flag and waits `TMLoadingOverlay.presentationDelay` before the synchronous main-actor work, so the overlay is drawn first (log: *Loading overlay around sessions*).
- **Completion.** An activity's terminal outcome is completed, skipped or interrupted, recorded once per execution identity. Completion enters the set page, rest (the plan's short rest in seconds, guided breathing: 6 s inhale and 3 s exhale) and the next set or activity automatically. Pause/stop win over completion in the same turn. Skip records the remaining sets as skipped. Stop records a stopped session with completed work.
- **Sets.** 1–5 sets per exercise (default 1), goals per set. A one-side activity counts its own goal. A bilateral arm raise, elbow bend, directional reach or fold towel is one activity (`SessionActivity.alternatesSides`, run by `AlternatingSidesActivity`), like Balancing: each side calibrates in turn before one countdown, each with the full calibration intro (`calibration.intro`, then that side's opening and demonstration cards; reach names the arm first), the set starts on the first side, the other side takes over after every credited repetition (narrated `session.switchArm.<side>`, towel `recovery.<side>`), and the goal counts both sides together. Calibration is kept between sets and invalidated by camera discontinuities or explicit recalibration, which recalibrates both sides (logs: *Bilateral exercises alternate sides*, *Calibration intro for each side*).
- **Daily plan.** `DailyPlan.standard` begins with thumb opposition, then arm raise, then the remaining finger and forearm exercises, elbow bend, directional reach, the shoulder/trunk exercises and fold towel. Only a session that reached its goal marks its item done. After a set summary (`DailyPlanTiming.completionPreview`, 4 s) the plan shows a narrated long rest of 2–6 breathing cycles (Settings' long rest, default 6; 3 s inhale, 2 s hold, 5 s exhale, 2 s pause; the recorded "six breaths" line plays only for six), then the next intro with a ten-second countdown that opens the session. Progress is kept per day in one versioned file (`daily-plan-progress.json`, version 2: each day's completed and planned item IDs, at most 730 days; a version 1 file is read as one day) (log: *Progress calendar and day pages*). Settings' one Exercises section is the only place for exercise preferences, in every build: the plan's order and which exercises it shows (`DailyPlanLayout`, `practice.planLayout`, through Arrange), each exercise's side (right, left or both; sit to stand has none), sets and repetitions (`DailyPlanViewModel.side(for:)`, `counts(for:)`; UserDefaults `practice.side.<id>`, `practice.sets.<id>`, `practice.repetitions.<id>`), and, in its Rest section, one plan-wide short rest between every set (5–120 s, default 15; `shortRestSeconds`, `practice.shortRest`) and one long rest between exercises and sides (2–6 breaths; `longRestBreaths`, `practice.longRestBreaths`) (log: *Plan-wide short and long rest*). Changes save at once and apply from the next session; while a plan runs the layout does not change. Without a choice an exercise keeps its program's own side and counts. Hidden exercises leave Beranda and the day's count. Reordering may place the scripted openers out of their written order (log: *One Exercises section in Settings*). Both sides alternate within one session, except a finger exercise and the Indonesian arm-raise briefs, which run one session per side (left, long rest, right) and mark the item done after the last side (log: *Per-exercise sides and counts*).

## 6. Exercise rules

Common body rules:
- `BodySubjectSelector` locks to the patient by torso position and shoulder width, never adopts a bystander for being larger, and relocks only after `relockTimeout` (5 s) without them. The usual place only arbitrates between several people: a sole person in view is followed by frame-to-frame continuity alone, so standing up keeps the lock. The continuity gate is per 1/30 s frame and widens with skipped frames up to three; shoulder widths within 0.03 image heights always match, so a side view's nearly overlapping shoulders do not break identity (log: *Steadier sit-to-stand at 1 m*). Each new lock increments `TrackingObservation.subjectEpoch`. Body inference runs on frames padded downward by 50% (`BodyFramePadder`; `-Tuntun.bodyFramePadding NO` disables it).
- `MovementLandmarkSmoother` filters joints with `OneEuroFilter.bodyJoint`, keeps a joint through one- or two-frame dropouts, and holds back a single jump over 0.15 until the next frame confirms it within 0.06.
- Finger exercises and fold towel use one indicator, `TMTherapyMergingGuide`, in `TherapyPalette.guidanceOrange`: the tracked point (fingertip or hand) is a circle that flows into its target circle as it arrives and is one circle while it counts as inside (log: *Merging indicator for every exercise*).
- Body exercises (arm raise, elbow bend, directional reach and Balancing) draw only the bubble indicator over the camera, `TMSessionBubbleOverlay`: a 44 pt joint circle that merges into the active bubble (`TMTherapyMergingGuide`, orange) and is one with it while inside or holding, a quiet outline for the other bubble, the hold as the guide's arc and a pop on acceptance, over the previous blue guidance arrows (`TMSessionGuideArrows`: the curved arrow to the active bubble, the calibration cue fixed to the body and the reach direction). No skeleton, hold count or farthest marker (logs: *Body exercises without camera overlay*, *Body target bubble restored*, *Body guidance arrows restored*). Bubbles are 100 pt across (`sharedBubbleDiameter`) and never move; acceptance uses the drawn radius. An accepted hold keeps its guide until the next frame, so every acceptance pops, also when a line starts speaking at that moment, and each completed calibration capture pops its capture circle (`MovementSnapshot.captureCompletions`). Sit to stand draws its hip as one 72 pt circle, smaller than the bubbles so it reads as the tracked hip. Calibration asks for the seat first (held, the arc fills), then a stand under an up arrow (held), then sitting back down under a down arrow before the countdown. Sit to stand draws no posture label or badge over the camera (log: *Sit-to-stand posture badge removed*). Practice splits each repetition into two halves: the arc fills from empty as the patient rises and pops on reaching the stand, then fills again as they sit and pops on the count. The held seat, the held stand and each practice stand play `hold-pop` ahead of the next instruction; the count keeps its chime and line. The up arrow runs from the seated to the standing hip position and the down arrow back; neither shows during holds, the countdown or lost tracking. While a repetition can no longer count or the patient is returning to the seat, the circle is a quiet outline with no arc (logs: *Sit to stand repetition arc*, *Sit to stand calibration and milestone pops*).
- No exercise draws instruction text over the camera: the video-attached live layout (Finger, Balancing and light guided sessions) has no caption and the guided opening and demonstration cues have no card; narration speaks them (logs: *No instruction caption on the camera*, *No calibration card on the camera*).
- Holds are credited only between consecutive fresh in-zone samples (`InterruptibleHold`, `StableHold`); interrupted time is never credited. Hold seconds are shown, not spoken (except in the Indonesian scripts, section 7).
- On iPad every exercise uses the front camera: body exercises prefer ultra-wide, hand exercises wide-angle.
- Finger guidance draws in `TherapyPalette.guidanceOrange` (rings, arcs, connectors); joint dots stay yellow. In thumb opposition the thumb and target circles are one `TMTherapyMergingGuide`: they merge by fingertip gap alone, starting at 0.75 palm lengths and one circle at 0.45 (the distance up to which a contact is kept), and part again as soon as the tips separate. The finger overlay draws only the fingertip (or whole-hand) circles, with no skeleton lines or joint dots. Full fist, hook fist and forearm rotation draw the whole-hand circle as a single `TMTherapyMergingGuide` circle with no fill, centred on the middle knuckle. In forearm rotation it is 2.3 palm lengths across and stays one size while the hand turns. In full and hook fist it follows the grip: from 1.3 palm lengths around a fist to 2.3 around an open hand, by `FingerActivity.gripOpenness` (the filtered grip metric between the patient's calibrated start and target poses, or a nominal 0.10–0.50 range before calibration). The circle glides between camera frames (`glide`, a 0.15 s spring without bounce; placed at once under Reduce Motion) (logs: *Smooth whole-hand circle*, *Whole-hand circle follows the grip*). A completed hold pops: `TMTherapyPopBurst` on the circle and the `hold-pop` sound. In thumb opposition an open-hand hold needs the thumb at least 0.60 palm lengths from the fingertip (log: *Merging thumb-opposition guide*).
- Body demonstrations for the seated exercises (arm raise, elbow bend, directional reach, cross midline, external and internal rotation, shoulder flexion) are framed from the waist up, so the standing rig does not suggest standing practice. Sit to stand keeps the full body. Framing and export live in `Tools/author_body_demonstrations.py` (log: *Torso-framed demonstrations*).
- Body demonstrations loop on the intro and demonstration card but hold the target pose during practice (arm raise and elbow bend also hold the start or peak pose being calibrated; reach holds the current direction; Balancing loops while calibrating). Peak times follow the authoring tool's keyframes (log: *Still demonstration during practice*).
- Body arm clips show the right arm and are reflected for a right-side exercise and shown as is for the left, so the demonstrated arm matches the patient in the mirrored camera preview; sit to stand is never reflected (log: *Demonstrations mirror the patient*).

| Exercise | Current rules |
| --- | --- |
| Arm raise, elbow bend (`MovementActivity`) | Hip–shoulder–elbow / shoulder–elbow–wrist, offsets normalized by the reference segment (> 0.03). Confidence: hip and shoulders 0.3, elbow and wrist 0.2. Start and target capture: 2 s steady holds; target distinct from start by > 40% of limb length; practice target at 100% of the held endpoint (`targetFraction`). Repetition dwell 2 s in each zone; leaving freezes the dwell up to 0.4 s, a tracking gap up to 0.5 s; longer resets to start. Tracking-lost message after 1 s, cleared after 0.5 s. |
| Directional reach | Start hold 2 s inside the drawn bubble. Each direction (right, left or across, up) runs 8 usable seconds; the target is the farthest sustained reach (within 45° of the direction, beyond two body radii, held 0.3 s), at 100% (`practiceTargetFraction`). Practice bubbles 120 pt. Each direction's window starts when its cue ends or as soon as the wrist leaves the start bubble, whichever is first; the start hold never waits for its cue. Rehearsal precedes practice; arrival dwell 2 s; outward budget 12 s per attempt, recorded reached, not reached or unscored. Evidence clears after 1 s without frames. |
| Balancing: cross midline, external/internal rotation, shoulder flexion, sit to stand | Own engines driven by `BalanceSessionViewModel`; `BalancePracticeSettings` (repetitions, hold, arm selection, sets 1–5, rest 5–120 s). Accept against the drawn bubble with a larger exit radius once a hold starts. Saved through `SessionRepository` as one-exercise routines. Sit to stand can be framed from the torso at the product owner's intended roughly 1 m setup: a current shoulder and hip on the same side, both confidence ≥ 0.3, are the minimum evidence throughout sitting and standing. Knees are optional (confidence ≥ 0.2); they can reject an obviously standing initial pose and supply the shoulder–hip–knee diagnostic angle, but never drive calibrated progress. Missing knees produce no angle rather than a fabricated joint. Hip displacement is normalized by the captured seated trunk length. Calibration needs hip rise ≥ 0.25 seated trunk lengths, shoulder rise ≥ 0.25, trunk scale 0.7–1.35 of the seated trunk and absolute lean ≤ 40° at the standing endpoint; practice uses calibrated hip travel and the same torso corroboration before accepting a stand. The 3 s holds use trunk-scaled tolerances. Missing shoulder/hip evidence cannot score. With only torso evidence the app estimates vertical torso travel; it cannot independently verify knee extension or a chair contact. A stationary camera and both torso landmarks staying in frame are required; 1 m is a setup intent, not a measured or guaranteed camera range (log: *Torso-only sit-to-stand detection*). Ankles and feet are never read. Once the seat is captured only that side is followed. A brief loss of the torso keeps a hold alive up to 0.4 s without crediting the gap, and keeps the drawn hip without a tracking-lost message for 0.5 s; longer losses clear the hold and the current repetition. Only a knee at confidence ≥ 0.3 can reject the seat as already standing. The seated and standing references are the mean hip of their 3 s holds (log: *Steadier sit-to-stand at 1 m*). The standing calibration hold starts only once the hip has set no new peak (more than 0.03 seated trunk lengths above the previous one) for 0.3 s, so its arc fills from the arrival; a running hold ignores samples straying beyond its tolerance for up to 0.25 s, which earn nothing. In practice the rising half's arc runs from the seated threshold (0.2 of calibrated rise) to the standing one (0.75), mirroring the lowering half (log: *Sit-to-stand hold arc in step*). Calibration holds the seat and the stand 3 s each; the stand hold is required. Any controlled stand and sit counts: no forward lean is required, and only an abrupt descent (under 0.5 s) is not counted (log: *Sit to stand calibration and milestone pops*). |
| Fold towel | One selected hand pinches (thumb–index ratio ≤ 0.25 to start, ≥ 0.55 open) in the grab zone to grab at once, slides to the goal, and opens for 300 ms to fold; four folds make one repetition. Only the current zone is drawn, as a circle as tall as the region with its step glyph; a plain 48 pt hand circle stays on the hand and joins the zone only while within the 0.12 acceptance distance (log: *Calmer fold-towel indicator*). Palm-centre cursor filtered by `HandCursorFilter`; 300 ms loss grace with 200 ms reconfirmation. One spoken cue per set plus at most one reminder (`TowelSpeechPolicy`). |
| Finger exercises, forearm rotation | Chirality voted by `HandSideStabilizer`; scored metric smoothed by `FingerMetricFilter`; opposition counts real contact only (≤ 0.35 palm lengths to start, ≤ 0.45 to keep); calibration needs a change > 0.15. Inference at 30 Hz. |

Older and superseded values (3 s captures, 75%/85%/90% targets, 68–120 pt clamp, 60 s relock, chevron arrows, wind cue) are in the log.

## 7. Audio, narration and voice commands

- **One configuration.** `NarrationAudioSession` alone sets the category: `.playAndRecord`, `.default` mode, `[.defaultToSpeaker, .allowBluetoothA2DP]` (plus HFP for finger sessions), `.playback`/`.spokenAudio` until microphone permission is granted. Receiver output is moved to the speaker. Voice processing is off (`-TuntunVoiceProcessing` enables it in Debug). Activation is counted so a late deactivation cannot mute the next session. `setCategory` and `setActive` block, so neither runs on the main thread: main-actor callers await `NarrationAudioSession.activate()` and deactivate through `deactivateInBackground()`, both on one serial queue; only `AudioInputWorker` activates synchronously on its own queue (`activateBlocking`) (logs: *Faster exit after End*, *Audio session off the main thread*).
- **Voice commands.** Exactly two English words in both languages, matched as the whole utterance through `VoiceCommandVocabulary`: "stop" pauses (interrupting narration) and "go" resumes when resumable. Everything else is touch-only. Recognition is on-device en-US with `requiresOnDeviceRecognition`. Every session listens: finger sessions no longer read the saved routine's legacy `voiceControl` (log: *Finger sessions always listen*). Settings shows Voice control as a toggle that cannot be switched off. It is on when microphone and speech recognition are both allowed; otherwise it shows why, with Enable permissions or Open Settings (nothing when restricted), and it rechecks when the app becomes active (log: *Voice control in Settings*).
- **Recorded narration.** Instructions play bundled recordings (`NarrationClips.resourceName(for:language:)`, `NarrationID`, `NarrationEN`) when every line of a cue has one; otherwise the system voice speaks the whole cue. Indonesian is spoken by Marizka, English by Katherine, a native American-English voice, so each language keeps one speaker for instructions and numbers (log: *Native-English narration voice*). `speak.<key>` entries may change spoken wording without changing screen text. Counts and countdowns come only from the recorded number clips (1–100, countdowns 1–10, `MarizkaCounts/marizka-<language>-…`; the filenames keep Marizka's name in both languages), with system-voice fallback. Sets and repetitions are configurable, so a recorded sentence states a count only when it is true and other counts are spliced number clips (`ScriptedRepetitions`).
- **Scheduling.** Pause, Stop, voice "stop", interruption, recalibration, camera loss and the end of a session cancel narration at once. When the session moves on to a new cue, narration hands off instead (`SessionAudioService.handOffSpeech`, `GuidanceAudioService.speak`): a recorded line with at most 1 s left finishes and the next cue follows; otherwise it fades over 0.25 s (the system voice stops after its word) and the next cue starts 0.3 s later. Queued prompts and counts of the replaced cue are dropped, and a finger cue's remaining lines are dropped. Countdown numbers always cut at once (log: *Responsive narration hand-off*). Repetition counts are queued ahead of pending prompts (bounded to 32). Effects use separate players, ducked during speech; starting narration fades effects; the demo-change chime is the exception.
- **Indonesian scripts.** Approved UX-writing scripts drive Indonesian arm raise and thumb opposition (`ArmRaiseGuidance`, `OppositionGuidance`, `ScriptedRepetitions`). They follow the plan's set and repetition counts, speaking a recorded line only when its numbers are true and Marizka numbers otherwise. Their holds are 3 s with spoken remaining seconds; first countdown 3 s, next set 5 s; three narrated breaths between sets, followed by silence until the plan's short rest has passed (`BreathingRest`). Arm-raise lines follow the movement and hand off to the next line; they never hold evidence back (thumb opposition still waits for its lines). Without custom counts, plan arm raise runs two sets of five per arm (left then right when set to both sides, one arm per session).
- **Generation.** Developer-run tools only, with the API key in the environment: `Tools/generate_marizka_counts.py` for numbers, `Tools/generate_narration.py` (with `--language en`) and its wrappers for instructions, `Tools/normalize_narration.swift` for levelling. Both generators take each language's voice from `generate_narration.VOICE_NAMES`. Fill or retake single lines with `--only`, which records and levels only those clips. See AGENTS.md.
- **Narration registry.** `Tools/narration-registry.json` lists every narrated key: its group (`finger`, `body`, or an approved script, `opposition-left/right` and `arm-raise-left/right`, each with its own raw folder and cache), languages, format arguments, voice tuning (seed, speed, lead-in) and whether its text is on screen while spoken (`screen`, `partly` with a note, or `voice`). It holds no wording: the String Catalog is the only text source (the key for the screen, `speak.<key>` when the spoken words differ). The generator and its per-script wrappers read only the registry; a new narrated key is added there. `generate_narration.py --report` writes the review sheet `Documentation/NarrationScript.md` (log: *Narration registry*).

## 8. Persistence, history and recording

- Atomic, versioned JSON files through `Shared/Storage`. Missing files differ from unreadable or unsupported ones, which are never overwritten with defaults.
- **Routines:** `routines.json`, `routines-task-oriented.json`, finger routines. **Sessions:** `Sessions/` holds an active checkpoint and one immutable summary per session; finalization is idempotent by session ID; a checkpoint left by termination is finalized as interrupted on next launch (`HistoryRecoveryService`). Calibration is never persisted (ADR-004). **Finger sessions:** `FingerSessions/`; an unreadable checkpoint is set aside, never deleted.
- Summaries store the routine snapshot, dates, outcome and per-set results (`SessionActivityResult`, with `repMetrics`). History skips unreadable summaries and reports how many.
- **Key repetitions.** `KeyRepRecorder` keeps first, hardest and last repetition per set for every exercise: skeletons (`*.reps.json`, Int16-quantized Vision coordinates) and, optionally, privacy-filtered 320 px, 10 fps HEVC clips (`*.clips/`). A repetition keeps at most 60 s; the clip ring keeps 65 s. Skeletons save and clips encode in the background, outside the save queue (clips also off the repository actor), so they never delay a checkpoint, the final summary or the plan moving on; a failed replay is only logged (logs: *Clips never delay the final save*, *Faster exit after End*). Deleting a session deletes both; one clip can be deleted on its own from the exercise detail panel, keeping its skeleton (`deleteRepClip`) (ADR-008, ADR-009; log: *Delete a key-repetition clip*). The panel's "Hapus catatan latihan ini", confirmed first, deletes every session of that exercise on that day with its replays and clips, and removes the exercise from that day's plan completions; the confirmation warns when a session also held other exercises, which go with it (log: *Delete an exercise's day record*).
- **Progress tab.** `TMProgressHeaderCard` counts this calendar week's practice days and takes no taps; `TMMonthlyCalendar` marks each day completed (every item the plan showed that day reached its goal), partial (anything else practised) or nothing, from `PracticeHistory`, which joins finger sessions, guided and Balancing sessions and the plan's saved days. The Progress root, daily history page and outlined summary header use `TherapyPalette.progressCanvas` (#FFFFFF in light mode, system background in dark mode). The calendar has no outline. Both `TMMonthlyCalendar` and `TMHistoryCard` use the existing `TherapyPalette.canvas` background (#F9F9F9 in light mode, adaptive in dark mode; log: *Neutral history card and calendar surfaces*). A day's page ("Perkembangan latihanmu") lists one `TMHistoryCard` per practised exercise in the order first practised; every card opens that exercise's detail panel (`TMExerciseDetailView` in `TMDetailPanel`, floating over a frosted backdrop): the day's best repetition (≈ angle, % of calibrated range for fingers, or repetitions for fold towel), average seconds per repetition and time moving, each tile naming its figure above the value and saying under a rule what it measures (arm raise and elbow bend say where 0° is); the best repetition against the first session, the previous session or the latest a week earlier (`ExerciseProgress`, steady within 5° or 5%), chosen by a "Dibandingkan dengan:" menu and drawn as two key-repetition poses, named in a caption, beside a headline in the exercise's own words ("Lengan kirimu bisa terangkat 28° lebih tinggi", `ExerciseWording`), a trend of each session's best (up to ten, the baseline kept), insight rows, each led by its aspect (Tempo, Kestabilan, Daya tahan, Jumlah), for pace and volume against that baseline and for the day's consistency and stamina (first against last repetition), and a trend caption saying what a rising line means; the day's best value is shown once, never repeated in the call-out; and the day's first, hardest (default) or last key repetition, chosen with chips, as its clip or, by a "Tampilkan kerangka" switch, its skeleton (a shown clip has a "Hapus video" pill, confirmed before the clip alone is deleted), with a call-out that follows the choice in plain words: how long the move took against the day's average, and how far it reached against the baseline and the day's best. The title names the side when the day practised one. The finger and session report pages are no longer linked from the day page (logs: *Exercise detail panel*, *Readable exercise detail figures*). The Progress stack hides the Beranda/Progres tab bar while any child page is pushed: one `.toolbar(…, for: .tabBar)` outside its `NavigationStack`, driven by the router's path, never a modifier on the pushed page (log: *Progress calendar and day pages*).
- **Recording levels** (Settings › Rekaman latihan): none, skeleton only, or video (default) with face, background, both (default) or no censoring. Body clips fail closed for faces; hand clips rely on face detection alone. Sessions read the level once at start.

## 9. Debug-only tools

Compiled only under `#if DEBUG`: "Finish exercise" (records remaining sets as completed, deliberately inventing credit), "Start without narration" on the plan intro, `-TuntunScreen` galleries, intros and Settings and audio comparison flags. Release builds contain none of them. Beranda also offers "Coba Berdiri dari Duduk" / "Try Sit to Stand", using the existing marked debug control to open that plan item's normal intro directly, regardless of the earlier items' state. It is disabled if sit to stand is hidden from the plan. It uses the existing router/readiness/calibration/session flow and neither reorders items nor marks preceding exercises completed (log: *Debug sit-to-stand shortcut*).

## 11. Verification

- No automated test target. Verify with `xcodegen generate` and a Simulator build with `IPHONEOS_DEPLOYMENT_TARGET=17.0`; temporary harnesses over production logic files are allowed outside the repository.
- A Simulator build never establishes camera, voice, animation, timing or offline acceptance. Physical M1-iPad checks are recorded with device, OS, app version, scenario and result.
- Outstanding device checks are listed in each log entry's verification paragraph. The standing matrix: movement and reach acceptance, geometry in both orientations and mirrorings, both languages, Stop/Go during narration and self-trigger rejection, background/interruption/termination recovery, storage corruption and duplicate history, Reduce Motion and large text, and two-minute capture-age and thermal runs.
