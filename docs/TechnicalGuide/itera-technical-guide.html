How to read this guide

Chapters 1–4 are for anyone joining the project. Chapters 5–10 explain the exercise app that runs on the patient's iPad. Chapters 11–13 explain the doctor–patient system added on 11 November 2026 and the infrastructure behind it. Chapters 14–17 collect the decisions, what has and has not been verified, and day-to-day operating knowledge.

Every chapter follows the same pattern: what the part does, how it is built (with the files to open), why it was built that way, and the considerations or trade-offs a maintainer must keep in mind.

Keeping it current: when a decision changes, update SYSTEM_DESIGN.md first, then this guide's source (docs/TechnicalGuide/itera-technical-guide.html), and rebuild the PDF with docs/TechnicalGuide/build-pdf.sh.

Status words used throughout Verified means checked by a Simulator build plus, where stated, a temporary Swift harness over the production code. Pending means it still needs the physical M1 iPad (camera, voice, iCloud). A successful build never proves camera, voice or iCloud behaviour.

1About Itera

Itera is an iPad app for guided home rehabilitation. The iPad's front camera watches the patient, counts correct repetitions, guides them with calm visuals and Indonesian narration, and records progress the doctor can review.

Who uses it

PersonWhat they do in Itera
PatientFollows the exercises the doctor assigned, one after another, hands-free. Sees their own progress.
CaregiverPositions the iPad, helps with recovery actions (recalibrate, skip, pause) when needed.
Doctor / therapistSince ADR-008: assigns exercises, sides, sets, repetitions and rest per patient on their own iPad, and reads each patient's results and joint angles.

Exercises

GroupExercisesTracked with
Hand and fingersFull fist, hook fist, thumb opposition, finger spreading, extension sequence, forearm rotationHand pose (Vision or MediaPipe)
Arm and shoulderArm raise, elbow bend, directional reachBody pose (Vision 2D or 3D)
Balance and trunkCross midline, external rotation, internal rotation, shoulder flexion, sit to standBody pose
Daily taskFold towel (a virtual towel moved with a pinch)Hand pose through the body tracker

Cup practice (a Core ML cup detector) still exists in code but is no longer part of the daily plan or the doctor's catalog.

Product constraints that shape the code

  • iPad only, landscape only, iPadOS 17 minimum. The M1 iPad is the performance baseline. Mac Catalyst builds are kept as an explicit exception.
  • On-device and offline-first. All camera inference, speech and voice-command recognition run on the device. Sessions work without internet after setup. Video, audio, landmarks and per-frame measurement streams are never saved or sent.
  • Indonesian and English through String Catalogs. Voice commands stay English (en-US) in both languages.
  • Older patients. Large controls, calm guidance without error wording, readable at 1.5–2.5 m, narration recorded in a soft Indonesian voice.
  • Camera evidence is an exercise aid, not a clinical measurement. Angles in reports are labelled as camera estimates until validated against a goniometer.

Numbers

186 Swift files, about 33,700 lines, one app target, 22 design-system component files, about 80 commits by five contributors. Dependencies: Apple frameworks plus one Swift package, MediaPipe Tasks Vision.

Core patterns

PatternHow Itera uses itWhy
MVVM with Observation@MainActor @Observable final view models held by views through @State; @Bindable only for bindings. No ObservableObject.One source of truth for UI state; Observation tracks exactly what a view reads.
Combine for eventsCamera frames, availability, audio events arrive as publishers; view models subscribe and cancel on exit.Services produce streams; Combine handles threading and cancellation cleanly (ADR-003).
Composition rootAppDependencies constructs every service and repository once and injects them.No singletons or service locators; easy to swap a repository.
Protocols at real seamsRepositories (SessionRepository, DoctorPatientRepository …), TherapyActivity, PermissionManaging.Substitution where it matters, not one protocol per type.
Typed commands and eventsSessionCommand, SessionEvent, SessionSnapshot, SessionEffect. Never strings like "Pause".The compiler checks every command path.

Threading model

  • All engine mutations run on the main actor; engine work per frame stays short.
  • Capture and inference run on dedicated serial queues (Itera.bodyTracking, Itera.bodyInference, dev.itera.hand-camera). Late frames are dropped by the capture output, never queued.
  • Delivery to the main thread is a single replaceable pending frame, so a slow main thread sees the newest frame, not a backlog.
  • File I/O happens inside repository actors; CloudKit calls are async.

3Project setup, build and signing

The Xcode project is generated from project.yml by XcodeGen and is not committed. Every persistent project change goes into project.yml.

First build

brew install xcodegen          # once
cd ~/Developer/Itera
xcodegen generate              # after any change to project.yml, folders or resources
open Itera.xcodeproj           # Xcode resolves the MediaPipe package on first open

Command-line Simulator build used for verification throughout the project:

DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer xcodebuild \
  -project Itera.xcodeproj -scheme Itera \
  -destination 'generic/platform=iOS Simulator' \
  IPHONEOS_DEPLOYMENT_TARGET=17.0 CODE_SIGNING_ALLOWED=NO ARCHS=arm64 build
arm64 only on the SimulatorMediaPipe 1.2.2 ships an arm64-only Simulator slice. Build the Simulator for arm64 (Apple silicon Macs); an x86_64 slice produces linker warnings.

Signing and iCloud checklist

  1. Use a paid Apple Developer Program team. A free Personal Team cannot use iCloud at all.
  2. Your Apple ID must be a member of team A2WQZ32XVK with a role that may edit identifiers (Admin, or App Manager with Certificates, Identifiers & Profiles access). The plain Developer role usually cannot add capabilities.
  3. In the developer portal the App ID com.OneDihrection.Itera must have iCloud with CloudKit enabled and container iCloud.com.OneDihrection.Itera assigned. Xcode's automatic signing does this when the role allows it.
  4. Select the team in Signing & Capabilities, then Try Again. The "wildcard profile doesn't include iCloud" errors disappear once the bundle identifier registers.
  5. Run xcodegen generate again whenever the project file is regenerated; signing values come from project.yml, not from edits in Xcode.
Why the container name follows the bundle identifierThe entitlement uses iCloud.$(CFBundleIdentifier) and the code uses CKContainer.default(). Changing the bundle identifier in one place therefore changes the container everywhere; there is no identifier in Swift to forget.

4Navigation, design system and conventions

NavigationRouter

All navigation and modal presentation goes through the shared NavigationRouter (App/Navigation). Features never own a NavigationStack, destination registration or modal state.

  • Routes are cases of AppRoute (for example .planIntro(id), .fingerSession, .therapySession, .angleMeasurement, .doctorPatient(id), .connectDoctor). AppRouterView.destination maps each route to its view in one switch.
  • Stacks: homePath and reportsPath for the two tabs; presentedSheets and presentedFullScreenCovers as stacks of presentations.
  • Tabs depend on the role: patients see Beranda and Progres; doctors see one Pasien tab.
  • Daily plan keeps one full-screen cover while it moves between sessions, rest and the next intro; the router replaces the destination inside it so the presentation never flickers.

Why: one owner of navigation makes deep flows (plan → session → rest → next intro) predictable, and a session can never dismiss something it did not present.

Design system

Itera/DesignSystem holds every reusable control and style; its README is required reading before UI work. Components take values, bindings, content and actions only.

Code conventions (summary of AGENTS.md)

  • Every new file has a header with file name, actual author and date (Swift // Created by, YAML #, Markdown/HTML comments).
  • Readable multiline declarations, guard clauses, shallow control flow, generous blank lines; // MARK: - in long files; comments explain purpose and constraints, not syntax.
  • Readability and runtime performance are equally important; performance-driven complexity must rest on measurements or concrete constraints.
  • Library and API questions are checked against current documentation through Context7 (npx ctx7) before coding.
  • No automated test target: verification is a Simulator build plus temporary harnesses compiled with swiftc over production files, plus physical-device checks.

5Sessions and exercises

A session runs one or more activities through a fixed lifecycle. Each exercise owns its own state machine; the session owns ordering, sets, rest, pauses and results.

Three engines

EngineExercisesKey files
Therapy sessionArm raise, elbow bend, directional reach, fold towel (and legacy cup)SessionEngine, SessionProgress, MovementActivity, FoldTowelActivity, TherapySessionViewModel
Finger sessionSix finger and forearm exercisesFingerSessionEngine, FingerActivity, FingerSessionViewModel, HandCameraService
BalancingCross midline, rotations, shoulder flexion, sit to standBalanceMovementEngine implementations, BalanceSessionViewModel

Rules that protect the patient

  • Missing evidence never earns credit. Holds freeze during short losses (InterruptibleHold: 1.5 s tracking grace, 0.4 s zone-exit grace, at most 0.3 s credited per step) and clear after longer ones.
  • Freshness. Observations older than 300 ms, from a previous capture generation, non-finite or non-increasing in time are ignored for scoring.
  • Calibration, not clinical maxima. Start and target positions are captured from stable holds (2 s for arm movements and reach). Targets are "observed targets", never called range of motion.
  • Preview continuity. One camera preview stays mounted through guidance, countdowns, rest and pause; stage pages are overlays, so the camera never restarts between stages.
  • Explicit resume. Backgrounding pauses; nothing resumes automatically.

Daily plan

DailyPlanViewModel runs the day's exercises in order. Each item opens its intro, then its session; finishing leads to the narrated breathing rest (DailyPlanNextView) and the next intro with a 10-second countdown. Progress per day is saved in daily-plan-progress.json.

Since ADR-008 the items come from the doctor's prescription: each DailyPlanItem carries a PrescriptionItem with sets, repetitions (or rounds, towels), hold, side and two rests, and the three engines read those values when the session launches (chapter 11).

6Camera tracking pipeline

Two capture owners feed the engines: BodyTrackingService (body, towel hand mode, cup) and HandCameraService (finger exercises). Both use the front camera at 30 fps.

Coordinates

Domain coordinates are unmirrored, normalized image coordinates with the origin at the bottom-left (Vision's convention). Distances are aspect-corrected by multiplying x by width/height. Only the presentation layer mirrors for the front-camera preview, through CameraDisplayGeometry. Anatomical left and right come from the detected body or hand, never from screen position.

Subject selection

  • BodySubjectSelector locks onto the first patient by torso position and shoulder width, ignores larger bystanders, and re-locks only after five seconds without the patient. Each new lock increments subjectEpoch so smoothing restarts.
  • HandSubjectSelector prefers continuity, then the exercised side, then a clearly dominant hand; ambiguous scenes report no hand.
  • HandSideStabilizer treats Vision's chirality as a vote with a 0.6 s time constant, because touching fingers make it flicker.

Smoothing

FilterWhere and why
FingerMetricFilterScalar One Euro filter (1.2 Hz at rest, faster when moving) on every finger exercise's scored metric; restarts on gaps, finger changes and lost evidence.
MovementLandmarkSmoother / JointPositionFilterPer-joint filtering for body exercises; holds back a single jump larger than 0.15 until the next frame confirms it, so a joint briefly placed on the wrong limb is never drawn or scored.
HandCursorFilterAdaptive One Euro filter for the towel cursor; drawing and acceptance use the same filtered point.
HandOverlaySmootherDisplay-only smoothing of the finger skeleton.
Why filters run before scoring for fingers and bodyUnfiltered detector jitter pushed a held pose in and out of its zone, making holds feel unfair. The filters restart on any real gap, so they never blend across missing evidence or between people.

Two enums switch the detectors without changing any exercise rule. They exist for measurement trials on the testing-pengukuran branch.

The flags

Vision 2D versus 3D

Vision 2DVision 3D (iOS 17)

Design choice: with 3D, exercises still read 2D points from the request's own projection (pointInImage), so counting rules are unchanged; metric positions go to TrackingObservation.world and are used only by angle measurement.

MediaPipe hand landmarker

  • MediaPipeHandDetector runs the Hand Landmarker in video mode synchronously on the capture queue, at the existing 30 Hz cap.
  • MediaPipe's 21 landmarks use Vision's joint order, so it produces the same HandEvidence. The adapter flips the y origin, swaps handedness (MediaPipe assumes selfie-mirrored frames; Itera's are unmirrored), assigns confidence 0.9 to every joint of a reported hand (MediaPipe has no per-joint confidence), and fills HandEvidence.world with metric world landmarks.
  • The hand camera now captures 32BGRA, the only format MediaPipe reads; Vision accepts it too.
  • The model Resources/Models/MediaPipe/hand_landmarker.task (float16, 7.8 MB, Apache 2.0) is bundled; source and checksum are in the Models README.
  • If the model fails to load or a frame fails, the service logs and falls back to Vision.
Why MediaPipe at allVision's hand pose is 2D only. Finger joint angles bend largely toward the camera, so 2D angles understate flexion. MediaPipe's world landmarks give metric 3D finger joints from the same front camera, which is the strongest justification for the one non-Apple dependency.

8Joint-angle measurement

Angles are measured from the same frames as the exercises, held-averaged, and saved only as summary ranges: before practice (calibration) and through practice.

Calculation

  • JointAngleCalculator prefers metric 3D joints (.world3D) and falls back to aspect-corrected image points (.image2D), requiring confidence 0.5 like the exercises.
  • Body: elbow flexion (180° minus shoulder–elbow–wrist), shoulder elevation (hip–shoulder–elbow), knee flexion.
  • Hand: flexion of each finger's MCP, PIP and DIP (thumb MP and IP), and finger spread (index–little proximal bones).

Held readings

AngleHoldEstimator reports a value only after 0.8 s within 6° inside a one-second window, as the median of those samples. A gap over 0.3 s or a change of source ends the hold. Only held values update the range, so a fast swing or one misdetected frame never becomes the patient's maximum — the same way a therapist reads a goniometer while the patient holds.

Recording in sessions

RecorderWhat it records
StagedAngleTrackShared core: one angle's held range before practice and through practice.
FingerAngleRecorderPer finger exercise: full fist MCP + PIP; hook fist PIP + DIP; opposition thumb flexion; spreading spread; extension sequence MCP + PIP. Four-finger metrics average index to little. Forearm rotation has none.
BodyAngleRecorderArm raise → shoulder elevation; elbow bend → elbow flexion, on the configured side, cumulative across sets.

Calibration phases count as "before"; counted practice as "after"; countdowns, rest, feedback, pauses and timed practice end the current hold. Results are stored in FingerExerciseResult.angles and SessionActivityResult.angles as optional fields, so older history files still decode.

Where angles appear

  • Progres tab: finger history cards and session detail ("Sudut sendi"), and an arm section ("Sudut sendi lengan").
  • Doctor's patient progress view (chapter 11).
  • The trial measurement page (Beranda toolbar, angle icon): live, held, smallest, largest and range, with a backend picker, for comparison against a goniometer.
Not a clinical measurement yetEvery report labels angles 2D or 3D and notes they are camera estimates. Agreement with a goniometer, front-on and side-on, must be established on the device before any value is used clinically.

9Audio, narration and voice control

One owner of the audio session

SessionAudioService is the only owner of the audio session for therapy, Balancing and the daily plan (finger sessions use GuidanceAudioService through the same NarrationAudioSession rules). During a session the category stays .playAndRecord with .default mode and .defaultToSpeaker, so narration and music play at normal media volume while voice commands listen.

  • Starting narration fades out effects; clip players stamp every play with a token so a late callback cannot finish a newer cue.
  • Music ducks to 0.10 during cues. Counts are serialised ahead of prompts in a bounded queue.
  • Voice processing (echo cancellation) is enabled with minimal ducking of other audio.

Recorded Indonesian narration

Indonesian cues play bundled recordings when every line of a cue has one; otherwise, on failure, or in English, the best installed system voice speaks. Clip names come from NarrationClips.resourceName (key without format specifiers, plus -argument). speak.<key> catalog entries may change the spoken wording without changing the screen text.

export ELEVENLABS_API_KEY="your-key-here"     # in your own terminal; never committed
python3 Tools/generate_narration.py --dry-run  # list lines and characters
python3 Tools/generate_narration.py --groups finger,body,numbers

Pending render: breath counts 7–10 and the opening line for 1–10 breaths (doctor-chosen rests). Until rendered, the system voice speaks them.

Voice commands

SFSpeechRecognizer with requiresOnDeviceRecognition, English command phrases only (pause, resume, stop …), processed once per utterance and scoped by recognition generation. Camera, microphone, speech permission and on-device recognition are mandatory before therapy.

Rules

  • Distinguish a missing file from an unreadable or unsupported one; never overwrite unreadable data with empty defaults.
  • Persist stable identifiers and numbers, never localized strings.
  • New fields are optional so older files decode (sets, angles, only, prescription fields).
  • Calibration is never persisted for reuse after termination (ADR-004).

11Doctor and patient roles

ADR-008: one app, two roles. The doctor assigns; the patient performs and views progress. One doctor has many patients; each patient has exactly one doctor. Both use iPads.

Role

AppRole (app.role) is chosen on first launch on TMRoleSelectionView; a doctor also enters the name patients will see. TMContentView shows the role's root. Keluar (sign out) returns to the role choice without deleting local or cloud data; it is in the doctor's toolbar overflow and at the bottom of the patient's Settings.

Prescription model

Prescription          version · publishedAt · items (ordered)
PrescriptionItem      exercise (catalog id) · side (left | right | both | none) · firstSide
                      sets 1–5 · work (repetitions 1–20, rounds/towels 1–10)
                      holdSeconds 3–20 (balance, except sit to stand)
                      setRestSeconds 5–120 · breathsBeforeNext 0–10
ExerciseMeasures      the one table of units, ranges, hold and allowed sides per exercise
  • Versions are immutable. "Simpan & kirim" publishes the draft as version N+1; drafts never reach the patient. Results record the version in force when the session started.
  • The patient app validates every value with ExerciseMeasures and ignores an invalid version, keeping the previous one — data from iCloud is treated as untrusted input.
  • Finger exercises allow left or right only (finger sessions run one hand); sit to stand has no side; "both" expands into sequential side activities with the doctor's first side.

Doctor screens

  • TMDoctorHomeView: patients, link state, latest version, last session.
  • TMDoctorAddPatientView → TMDoctorPairingView: QR code and grouped 26-character code.
  • TMPrescriptionEditorView: catalog pane (shown only in doctor mode) and the patient's prescription; add by tapping or dragging, reorder by dragging, delete by swiping; total rest estimate; "Simpan & kirim".
  • TMPrescriptionItemEditor: side, first side, sets, unit, hold, set rest, breaths before next.
  • TMDoctorPatientProgressView: results newest first with sets, work, version and angle cards.

Patient mode

  • Beranda builds the plan from the prescription (DailyPlanViewModel.apply); a plan in progress keeps its items until it ends. Without a doctor it shows "Hubungkan ke dokter"; with a doctor but no prescription, "not assigned yet".
  • Session launch maps item values into FingerRoutine, RoutineExercise/Routine and BalancePracticeSettings; the engines are unaware of doctors or iCloud.
  • The breathing rest uses the finished item's breaths; zero skips straight to the next exercise announcement and 10-second countdown.
  • Side, sets, repetitions and rest controls are hidden from patient Settings.
  • AppDependencies.refreshCare() loads the stored link, fetches newer prescriptions and uploads new results on Beranda.
  • Debug builds launched with -IteraStandardPlan keep the fixed plan for testing sessions without pairing.

12Cloud infrastructure and encryption

Doctor and patient iPads exchange data through CloudKit's public database, end-to-end encrypted with a secret handed over in person. This is the ADR-008 revision of 11 November 2026.

Why the public database

The first implementation used CloudKit sharing: one zone per patient in the doctor's private database and a results zone in the patient's private database, each shared read-only. CloudKit counts private and shared records against the owner's personal iCloud quota; with a full iCloud, every write failed, even a few kilobytes. The public database counts against the developer's container quota, so a full personal iCloud no longer blocks the app. The public database is readable by every user of the app, so the revision adds end-to-end encryption.

The care channel

ElementImplementation (CareChannel)
Secret128 random bits from SecRandomCopyBytes, created on the doctor's iPad when the patient is added.
Hand-overOnly in person: QR itera-pair:<26 chars> or the same 26 base32 characters typed (grouped 5-5-5-5-6; 0/1/8 read as O/I/B).
Key derivationHKDF-SHA256 with salt itera.care; info names for record names, box for encryption.
Record names"c" + hex(HMAC-SHA256(namesKey, logical)[0..20]); logical names: offer, reply, prescriptions, results-yyyy-MM.
PayloadsAES-256-GCM with the logical name as authenticated data; fresh nonce per seal.
Storage of the secretKeychain, kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly, not synced; never in JSON files.

Records

One generic record type, CareRecord, with one field, box, so the schema itself reveals nothing. Records are fetched by name, never queried, so no indexes are required.

Operating the container

  • Development environment: the CareRecord type is created automatically on the first save from a Debug build.
  • Before TestFlight or App Store: in CloudKit Console, deploy the schema to Production; Release builds use Production and fail with a schema error otherwise.
  • Default public-database security roles (World read, Authenticated create, Creator write) must stay; they enforce who can change which record.
  • Watch the developer container's usage and request limits in CloudKit Console as patients grow.
  • Writes need a signed-in iCloud account on the device; reads do not; neither needs free personal space.

Error handling

CareCloudService.errorKey(for:) maps CloudKit codes to specific messages (no account, account needs attention, network, setup/entitlement, schema, quota, unknown), unwrapping partial failures. errorDetail(for:) adds "CKError N · system text" under the message and every failure is logged as CloudKit <step> failed: …. Only true network errors say "check the connection".

Threats and mitigations

ThreatMitigation / residual risk
Another app user downloads the public databaseNames are HMACs and bodies are AES-GCM; without a secret nothing is linkable or readable. Residual: record counts, sizes and times are visible.
Someone photographs the pairing codeShown only in person; the screen warns that it is the patient's key; offers expire after 10 minutes. Residual: the secret itself does not expire; a leaked code reads that patient's data.
Swapping or forging recordsAuthenticated encryption bound to the logical name; creator-only writes on the server.
Doctor edits results / patient edits prescriptionsServer-enforced creator rule; patient app also validates every value.
Lost device or resetKeychain items are this-device-only; a reset makes earlier cloud data unreadable and requires re-pairing.
Malformed or hostile prescriptionPrescription.isValid rejects unknown exercises and out-of-range values; the previous valid version stays.

Regulation

Rehabilitation data is specific (health) personal data under Indonesia's UU PDP No. 27/2022, and electronic medical records have Ministry of Health rules. The patient gives explicit consent on the consent card. Data is held on Apple's servers, encrypted, in a database every app user can technically download. Legal and clinical review is required before use with real patients.

17Known limitations and next steps

Limitations

  • Balancing sessions save no history, so their results are not sent to the doctor.
  • Results already in history before pairing are uploaded at the first sync.
  • The channel secret never expires; re-pairing reuses it.
  • A patient's replacement iPad cannot overwrite records made by the old one.
  • Refresh happens when Beranda or the doctor's list appears; there is no background push.
  • Narration for 7–10 breaths and the counted opening line is not rendered yet.
  • Angles are camera estimates without goniometer validation.
  • The prescription editor, drag and drop, and every CloudKit path are unverified on devices.

Recommended next steps

  1. Sign with team A2WQZ32XVK, run the full pairing and prescription flow on two iPads, including one with full personal iCloud.
  2. Run goniometer comparisons with the measurement page for each backend.
  3. Render the missing narration clips.
  4. Decide on secret rotation and device replacement before real patients.
  5. Add Balancing history if doctors need those results.
  6. Complete legal review (UU PDP) and deploy the CloudKit schema to Production before TestFlight.
  7. Consider CKSyncEngine or subscriptions if near-real-time updates become important.
